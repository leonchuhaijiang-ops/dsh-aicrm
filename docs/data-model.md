# 数据模型

> 一句话：**Excel 是唯一事实源**。插件、模型工具、看板都只是读写这些表的壳；表在你自己选的数据目录里，不在这个仓库里。
>
> 列名是**契约**——可以调换列顺序、可以改列宽，但**不要改列名、不要删列**。写入口会先断言表头，列名对不上会直接拒绝写入并报错，不会静默清空。

列名的权威定义在 `lib/sales-lib.js`（`HEADERS_MASTER` / `HEADERS_FLOW` / `HEADERS_CONTACT`），本文逐字照抄。

## 1. 数据目录结构

`npm run setup`（或看板里的首次设置向导）会在你指定的目录下建出这套骨架：

```text
<你的数据目录>/
├── 销售客户-主表.xlsx          # 客户主表：sheet「客户主表」31 列 + sheet「联系人」5 列
├── 销售客户-流水表.xlsx        # 跟进流水：sheet「跟进流水」11 列
├── 合同台账.json               # 合同要素、状态、付款节点（.docx 正文在 合同/）
├── 首访任务清单.json           # 首次触达的每日保底计数与今日清单
├── 用量快照.json               # 每日用量快照（周复盘做「变化」对比用）
├── 示例数据.json               # 仅在生成过示例数据时存在：登记 DEMO-xxx 的 ID 清单（清除依据）
├── .sales-lock                 # 进程间写锁，别删、别手工编辑
├── 营销资料库/                 # 话术/方法论语料（.md 与 销售技巧-结构化.json），RAG 只读这里
├── 合同/                       # 生成的 .docx 合同（只在本机生成，不上传）
├── logs/                       # 运行日志（只记元数据，不记客户正文）
└── 快照/                       # 历史用量快照归档
```

初始化是幂等的：已存在的文件**只保留、不覆盖**，重复初始化不会冲掉你的客户数据。

## 2. 客户主表（`销售客户-主表.xlsx` → sheet「客户主表」）

共 **31 列**：

| # | 列名 | 类型 | 说明 |
|---|------|------|------|
| 1 | 客户ID | 文本 | 主键。格式 `C-<地区或来源>-<YYMM>-<三位序号>`，例如 `C-示例-2601-001` |
| 2 | 公司 | 文本 | 客户公司全称；只有简称时也填这里的常见叫法 |
| 3 | 姓名/联系人 | 文本 | 主要联系人；不确定时留空，别编 |
| 4 | 手机 | 文本 | 11 位手机号；没有就留空（微信/短信通道仍可用） |
| 5 | 客户等级 | 枚举 | `SS` / `S` / `A` / `B` / `C`；留空 = 未定级。等级随六分类归一（见第 5 节） |
| 6 | 跟进状态 | 枚举 | `跟进中` / `挂起` / `重点跟进` / `挂起冷备` / `已闭环` / `待首触` |
| 7 | 触达状态 | 枚举 | `未触达` / `待微信通过` / `已加微信` / `已触达` |
| 8 | 下次跟进时间 | 日期 | `YYYY-MM-DD`；没有明确日期就留空（= 待定，不派活） |
| 9 | 下次跟进方式 | 枚举 | `电话` / `微信` / `上门` / `短信` / `合同` / `官网申请` / `其他` |
| 10 | 备注 | 文本 | 自由备注；写入口的追加备注也落这里 |
| 11 | 原编号 | 文本 | 导入前旧系统/旧表里的编号，用于追溯 |
| 12 | 建档日期 | 日期 | `YYYY-MM-DD` |
| 13 | 建档类型 | 文本 | 建档时给的类型，默认 `个人`；导入数据可自带 |
| 14 | 微信昵称 | 文本 | 加微信后记录的昵称，便于对号 |
| 15 | 城市 | 文本 | 客户所在城市 |
| 16 | 来源 | 文本 | 线索来源（渠道/活动/转介绍等，自己定口径） |
| 17 | 意向阶段 | 枚举 | 客户**当前**处在 SOP 哪一段（13 段漏斗或 2 个出口，见第 5 节） |
| 18 | 是否购买 | 文本 | `是` 表示真的付过费；其余视为未购买 |
| 19 | 付款总额 | 数字 | 单位：元；展示时会换算成「X.XX 万元」 |
| 20 | 责任人 | 文本 | 跟这个客户的人 |
| 21 | 放弃原因分类 | 文本 | 兼容列：留给导入的历史数据；当前版本用「结论」留痕记放弃原因 |
| 22 | 首访排期 | 日期 | 兼容列：当前版本的首访排期记在 `首访任务清单.json` |
| 23 | 注册时间 | 日期 | 客户在你产品上的注册日期（如适用） |
| 24 | 最后登陆时间 | 日期 | 产品侧事实字段，**只展示、不据此判定意向** |
| 25 | 到期时间 | 日期 | 产品/服务到期日，用于续费提醒 |
| 26 | 智算次数 | 数字 | 产品用量事实字段（如不适用可留空） |
| 27 | 智写登录次数 | 数字 | 产品用量事实字段 |
| 28 | 智写剩余字数 | 数字 | 产品用量事实字段 |
| 29 | 智写消耗字数 | 数字 | 产品用量事实字段 |
| 30 | 智写文章生成次数 | 数字 | 产品用量事实字段 |
| 31 | 智写购买字数 | 数字 | 产品用量事实字段 |

第 26–31 列是「产品用量」类字段：用得上就填（周复盘会拿来做用量异常观察），用不上整列留空即可，不影响其他功能。

### sheet「联系人」

同一工作簿的第二个 sheet，共 **5 列**，一个客户可以有多行联系人：

| # | 列名 | 类型 | 说明 |
|---|------|------|------|
| 1 | 客户ID | 文本 | 关联主表「客户ID」 |
| 2 | 姓名 | 文本 | 联系人姓名 |
| 3 | 手机 | 文本 | 联系人手机号 |
| 4 | 微信昵称 | 文本 | 联系人微信昵称 |
| 5 | 角色/备注 | 文本 | 决策角色（决策人/使用人/技术把关…）或备注 |

## 3. 跟进流水表（`销售客户-流水表.xlsx` → sheet「跟进流水」）

共 **11 列**，一次跟进一行，**只追加、不覆盖**：

| # | 列名 | 类型 | 说明 |
|---|------|------|------|
| 1 | 流水ID | 文本 | 主键，形如 `F-<YYMMDD>-<序号>` |
| 2 | 客户ID | 文本 | 关联主表「客户ID」 |
| 3 | 日期 | 日期 | 这次跟进发生的日期，`YYYY-MM-DD`（不传就留空，不自动填今天） |
| 4 | 方式 | 枚举 | `电话` / `微信` / `上门` / `短信` / `合同` / `官网申请` / `其他` |
| 5 | 类型 | 枚举 | `首触` / `试用回访` / `高意向跟进` / `老客服务` / `客户反馈` / `策略调整` / `放弃跟进` / `数据整理` |
| 6 | 沟通内容 | 文本 | 聊了什么 / 做了什么 |
| 7 | 对方反应 | 文本 | 客户的反应、原话要点 |
| 8 | 下一步动作 | 文本 | 接下来要做的事 |
| 9 | 下次跟进时间 | 日期 | 这次跟进后约定的下次时间 |
| 10 | 下次跟进方式 | 枚举 | 同上「方式」的取值 |
| 11 | 阶段 | 枚举 | 这次跟进**发生在**哪个 SOP 段（与主表「意向阶段」是两件事）。**空 = 未标注**：归不进 13 段/出口的记录留空，面板归到「其他跟进记录」 |

流水里还会追加两类特殊记录（同样落这几列，靠「类型/内容」里的标签区分）：**变更留痕**（改主表字段时自动写一条）与**结论留痕**（给客户点名结论时写一条，带复查锚点）。

## 4. 写入规则（为什么不要手工改表）

1. **写入口唯一**：所有写入走 `lib/sales-lib.js` 的四个写函数（`cmdLog` / `cmdAdd` / `writeMaster` / `writeFlow`），它们自带写锁、表头断言、原子写、变更日志。模型工具只是它们的调用方。
2. **写锁**：写操作会先拿 `<数据目录>/.sales-lock`，并发写会排队或明确报错，不会两个进程各写一半。
3. **表头断言**：写入前逐个核对关键列是否齐全、列名是否非空；对不上直接抛错，**不落盘**（防的是「读到的表头是空行 → 整表被覆盖成空表」这类事故）。
4. **原子写**：先写临时文件再 `rename`，中途断电不会得到半张表。
5. **日期口径**：一律 `YYYY-MM-DD` 文本，不写 Excel 日期序列号、不写「今天/明天」。
6. **列顺序可调**：读取按列名取值，不依赖位置；但**列名不能改**。

> 如果你要用 Excel/WPS 手工修数据：改完必须保持表头行原样。手工删列、改列名、把表头挪到第 2 行，都会让下次写入被拒绝。

### 关于 `lib/package.json`

数据层 `lib/sales-lib.js` 是 **CommonJS**，而仓库根的 `package.json` 声明了 `"type": "module"`。所以 `lib/` 下有一个只做一件事的 `package.json`：

```json
{ "name": "dsh-sales-lib", "private": true, "type": "commonjs" }
```

这是 Node 的标准约定（就近决定模块类型），**不是漏进来的杂项文件，别删**；删了 `node lib/sales-lib.js …` 会被当成 ESM 解析、直接报 `require is not defined`。路径和文件名都不变，命令行照旧：

```bash
node lib/sales-lib.js check --dir "<你的数据目录>"
```

`package.json` 的 `files` 已包含 `lib/`，所以这个嵌套 `package.json` 会随包一起发布。

## 5. 枚举取值

### 客户等级 ↔ 六分类（等级跟着分类走）

看板的六个客户页签就是六个分类，每个客户**必须落且只落一类**；等级由分类归一，不由人工另填：

| 分类（页签） | 等级 | 含义 |
|---|---|---|
| 定制开发 | `SS` | 企业级轨（私有化/定制），单独一条推进过程 |
| 标品成交 | `S` | 已付费成交，按周期做服务追踪 |
| 重点跟进 | `A` | 人工挑的重点盘子，不进今日任务，自己每天看 |
| 待定跟进 | `B` | 跟进中/挂起，距上次跟进超过一周再跟 |
| 挂起冷备 | `C` | 已停跟，不派活不提醒，只在新功能上线时人工捞回 |
| 待首触 | 不定级 | 还没第一次触达 |

### SOP 阶段（主表「意向阶段」、流水「阶段」）

标品轨 7 段 + 企业级轨 6 段，共 13 段有序漏斗，外加两个出口（终态）：

```text
线索获取 → 客户触达 → 需求挖掘 → 产品演示 → 异议处理 → 方案报价 → 成交签约
        → 企业级机会 → 决策链摸排 → 需求与现状勘察 → 方案与试点设计 → 商务推进 → 私有化签约
出口：无法联系 / 推进终止
```

旧叫法（`兴趣` / `预约演示` / `价值传递` / `成交` / `企业版` / `POC` 等）在写入时会自动归一到正式值，不会被当成非法值拒掉。

**归不进这 13 段、也不属于出口的记录**（老数据没写阶段、随手记的行业闲聊、跨段的杂事）：流水「阶段」写空，看板 SOP 面板底部归到「其他跟进记录」；写日志时显式传 `stage: '其他跟进记录'` 即可（`其他` / `未归类` 同义）。这条记录**不会推动主表当前阶段**。

### 跟进状态

| 值 | 含义 |
|---|---|
| `待首触` | 还没第一次触达 |
| `跟进中` | 已经接触，下次时间确定 |
| `挂起` | 已接触、有跟进意愿，但下次时间不确定 |
| `重点跟进` | 人工重点盘，不再提醒跟进 |
| `挂起冷备` | 先不跟了 |
| `已闭环` | 有结果了（成交 / 终止 / 无法联系） |

**挂起类状态必须有据**：要么流水里有【结论】留痕，要么本次同时把阶段推到出口。否则写入口会拒绝——这是为了堵住「状态挂了却没说为什么」的黑洞。

## 6. 表头契约（给改代码的人）

- 权威常量：`lib/sales-lib.js` 的 `HEADERS_MASTER`（31）、`HEADERS_FLOW`（11）、`HEADERS_CONTACT`（5）。
- 新建空表必须用 `aoa_to_sheet([headers])`，**禁止**用 `json_to_sheet([])` 推表头、**禁止**拿 `rows[0]` 当表头。
- 表名固定：`客户主表` / `联系人` / `跟进流水`（`npm run doctor` 会核对）。
- `npm run doctor` 会逐字比对表头与契约常量；改列名必须先改常量，再迁移数据。
