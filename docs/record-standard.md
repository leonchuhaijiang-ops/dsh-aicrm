# 跟进记录填写标准

> 一句话：一条跟进记录必须能回答「**谁、什么时候、说了什么、下一步干什么**」。答不上来，就不算一条记录。

这份标准管两件事：**人**怎么记（确认卡上填什么），**模型**怎么记（`sales_log` 传什么）。两者是同一套字段——你在卡上改过的值，就是最终落库的值。

## 1. 为什么要有标准

跟进记录不是流水账，它是下游所有功能的原料：

- 今日队列靠它算「多久没联系、该不该再跟」；
- 作战卡靠它回顾「上次说到哪、客户卡在哪」；
- 周复盘 / 飞轮靠它算推进、停滞、结论与转介绍；
- 下次通话时，你（或模型）读的也是它。

**垃圾进，垃圾出**：一条「聊了聊，还行」会让下次跟进从零开始，也会让周复盘统计失真。所以宁可字段少，不要字段假。

## 2. 九要素

> 文档里的手机号一律打码成 `138****0000`；实际传入的是 11 位数字，不要带 `*`。

| # | 要素 | `sales_log` 入参 | 必填 | 缺失 / 留空时行为 |
|---|------|------------------|------|-------------------|
| 1 | 客户 | `phone` | **必填** | 11 位手机号；格式不对、库里找不到 → **拒写**并提示。一个手机号 = 一个客户，重复号会被体检标红 |
| 2 | 事实 | `what` | **必填** | ≥ 8 字，写清「谁说了什么 / 你做了什么」；太短 → **拒写**并提示补实质内容 |
| 3 | 日期 | `date` | 可空 | 缺省 = **今天**；补历史记录时显式给 `YYYY-MM-DD` |
| 4 | 方式 | `method` | 可空 | 留空 = 不猜（不会默认成「电话」） |
| 5 | 类型 | `type` | 可空 | 留空 = 不猜 |
| 6 | 反应 | `react` | 可空 | 留空 = 不编客户的态度 |
| 7 | 环节 | `stage` | 可空 | 判不出 / 跨段 → 落「其他跟进记录」**待归段**（见第 6 节）；不传 = 客户当前阶段不动 |
| 8 | 下一步 | `nextAction` | 可空 | 留空 = 这次没约定下一步 |
| 9 | 下次跟进 | `nextDate` / `nextMethod` | 可空 | 留空 = **主表原排期不动**；要清空排期得显式传 `待定`（见下表） |

**这是「软强制」：只有前两项会硬拒，其余留空只提示、不拒写。** 因为强制填全的结果一定是编造——「反应」「下一步」这种字段，没有就是没有。

`nextDate` 的三态别搞混：

| 你传了什么 | 结果 |
|---|---|
| `"2026-11-18"` | 排期写成这天 |
| `"待定"` / `clearNext:true` | **清空**排期，客户进「待定跟进」区 |
| 什么都不传 | 主表原排期**原样不动**（不是清空） |

## 3. 和确认卡的关系

在 AI 助手输入框里**说一句话**就行，不用填表：

```text
今天给示例咨询有限公司的张工打了电话，他说园区试点明年一季度有预算，
让我们下周把方案发过去，下周三再跟。
```

```text
你说一句话
  → 助手按九要素抽字段
  → 确认卡（9 个字段都能改，卡头显示「已填 N/9」）
  → 你点确认
  → 插件一次写主表 + 流水表
  → 回执：已写进客户表（主表+流水表）· 手机 138****0000
```

几条约定：

- **卡是给你改的**：抽错了、漏了，直接在卡上改，确认时按改后的值写。
- **缺项只提示**：卡上标出未填项，不挡确认。
- **写失败不清卡**：网络/写锁/表头断言失败时，已填内容保留，改完重试即可。
- **不显示内部编号**：确认卡、回执、客户标题里只有手机号与公司/联系人，不出现 `C-…` 这类存储主键。

模型侧对应的是 `sales_log`（参数表见 [模型工具清单](./tools.md)）。助手是你和 `sales_log` 之间的翻译层：它负责把一句话拆成九要素，写库仍是 `sales_log`。

## 4. 正例 3 条

### 正例 1｜电话首触

**你说**：

```text
今天给示例咨询有限公司的张工打了电话，他说园区智慧化试点明年一季度有预算，
让我们下周把方案发过去，下周三再跟。
```

**抽出的九要素**：

| 要素 | 值 |
|---|---|
| phone | `138****0000` |
| what | 张工反馈园区智慧化试点明年一季度有预算，要求下周先发方案 |
| date | 2026-11-11（缺省今天） |
| method | 电话 |
| type | 首触 |
| react | 有明确预算窗口，愿意见方案 |
| stage | 需求挖掘 |
| nextAction | 整理园区试点方案并发给张工 |
| nextDate / nextMethod | 2026-11-18 / 微信 |

**为什么合格**：有具体人（张工）、具体事（发方案）、具体时间（下周/下周三）。“有预算”是客户原话，不是推断。

### 正例 2｜价格异议

**你说**：

```text
张工微信上说我们报价比另一家高两万，我解释了含三年运维，
他说要拿这个理由去跟领导申请，让周五前给他一份分项报价。
```

**抽出的九要素**：

| 要素 | 值 |
|---|---|
| phone | `138****0000` |
| what | 张工反馈报价比竞品高约两万；我方说明含三年运维；客户要求周五前给分项报价用于内部申请 |
| method | 微信 |
| type | 高意向跟进 |
| react | 价格敏感，但愿意推进内部流程 |
| stage | 异议处理 |
| nextAction | 出分项报价（把运维拆开列） |
| nextDate / nextMethod | 2026-11-13 / 微信 |

**为什么合格**：把「异议是什么、我怎么答的、他要什么」写全了；下一步是可执行动作，不是「再联系」。

### 正例 3｜老客续费（不硬塞段）

**你说**：

```text
给示例制造有限公司的李经理打了电话，服务下月到期，他说用得还行，
续费要走采购流程，让我把续费单先发过去。
```

**抽出的九要素**：

| 要素 | 值 |
|---|---|
| phone | `138****0001` |
| what | 李经理确认服务下月到期、使用正常；续费需走采购流程，要求先发续费单 |
| method | 电话 |
| type | 老客服务 |
| react | 正向，流程驱动 |
| stage | 成交签约 |
| nextAction | 发续费单并跟进采购节点 |
| nextDate / nextMethod | 2026-11-14 / 微信 |

**为什么合格**：到期日、流程卡点、下一步都写清了。如果当时聊的是「行业展会、跟单子无关」，那就**别硬塞段**——`stage` 留空/落「其他跟进记录」，之后再归段。

## 5. 反例 3 条

### 反例 1｜空话

```text
聊了聊，还行，说再看看。
```

- **问题**：`what` 不到 8 字且没有实质信息；谁说的、看什么、什么时候再看，全都不知道。
- **后果**：下次打电话你还是不知道上次聊到哪；周复盘把它算成一次「有效跟进」，掩盖了真实停滞。
- **改法**：至少补成「张工说方案先留着，等他们内部立项会（下月）后再谈；让我下月 5 号再问」。

### 反例 2｜编造

客户原话只有「预算要报上去」，记录写成：

```text
客户已确认预算 36 万，下周一签约。
```

- **问题**：「确认预算」「签约」都是记录者脑补的；金额与日期没有来源。
- **后果**：漏斗被伪造（阶段虚高）、周复盘「推进」虚增、下次话术按「已成交」口径说，客户当场翻脸。
- **改法**：只写听到的——「预算需上报，具体金额与审批时间未定」；推测写进 `nextAction` 并标「待确认」，别写成事实。

### 反例 3｜把系统留痕当跟进

改主表字段、给客户点名结论时，插件会自动写「变更留痕 / 结论留痕」。有人为了「让这个客户看起来有记录」，再补一条 `what="更新了客户信息"`。

- **问题**：系统留痕不是跟进——它记录的是「数据被改过」，不是「你和客户发生了什么」。
- **后果**：今日队列误判「刚联系过」而不再派活；SOP 面板里混入噪声。实际上 SOP 面板已经**不上屏系统留痕**，补了也只会污染统计。
- **改法**：没有实质沟通就不记。真要留个说明，写在客户档案或备注里，不要冒充跟进。

## 6. 「其他跟进记录」= 待归段

不是每次跟进都对得上 13 段漏斗（标品 7 段 + 企业级 6 段）或 2 个出口。这类记录不硬塞，统一落「其他跟进记录」：

- **什么时候落**：判不出段、跨段杂事、老数据没写阶段、行业闲聊。
- **不是垃圾桶，是待办区**：桶里每一条都该被归段，**目标清零**。SOP 面板的桶标题就是「其他跟进记录（N 条）· 待归段，目标 0」。
- **怎么归段**：SOP 面板每条记录右侧有「归段」下拉（13 段 + 2 个出口），选中即调：

```text
POST /sales/stagefix
{ "phone": "138****0000", "flowId": "F-261111-003", "stage": "异议处理", "reason": "补标注" }
→ { "ok": true, "data": { "from": "", "to": "异议处理" } }
```

归段只改**这一条历史记录**的「阶段」标注；它不代替一次新跟进，也**不推进主表当前阶段**。要让客户当前阶段前进，另记一条带 `stage` 的跟进（或走结论）。

- **系统留痕不参与**：变更/结论留痕不出现在 SOP 列表里，不需要也不能归段。
- **看板之外的自检**：

```bash
npm run audit          # 逐客户核对：跟进条数 = 段内 + 其他跟进记录
npm run backfill       # 历史记录补阶段（默认 dry-run，只列不改；确认后加 --apply）
```

## 7. 手机号是客户标识

- **认客户只认 11 位手机号**：对话、确认卡、客户卡、SOP 都传手机号；没有手机号的客户会标「⚠ 缺手机号」，请先补。
- **客户ID 是内部主键**：`C-…` 只用于两张表互相关联，不对用户、也不对模型出现。你不需要知道它，也不该在对话里看见它。
- **一号一客**：同一手机号不允许出现在两行客户里。`npm run doctor` 会查重复号（重复即失败）与空号（只提示）。

## 8. 一句话速查

```text
手机号 + 事实（≥8 字）必须有；
日期不填算今天；下次跟进不填=排期不动；
判不出环节就留空，落待归段，之后在 SOP 里归；
没有实质沟通就别记；系统留痕不算跟进。
```
